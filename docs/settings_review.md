# Settings Review — `config/settings.py`

This document reviews `config/settings.py` against current Django best practices
(Django 4.x / 5.x).  Each item describes the current state, the recommended change,
and why it matters.

---

## 1. Missing `DJANGO_SETTINGS_MODULE` Split

**Current state:** All environment-specific config is controlled via `if ENVIRONMENT == "production"` branching inside a single file.

**Best practice:** Use separate settings modules — `base.py`, `development.py`,
`production.py`, `test.py` — and set `DJANGO_SETTINGS_MODULE` accordingly.  This is
the approach recommended by the [Django deployment checklist](https://docs.djangoproject.com/en/4.2/howto/deployment/checklist/).

**Why it matters:** Branching logic in a single file makes it easy to accidentally
introduce production configuration into development (or vice versa) and harder to audit
each environment's full effective configuration.

## 2. Hard-Coded `SECRET_KEY` Fallback

**Current state:**

```python
SECRET_KEY = os.environ.get(
    "SECRET_KEY",
    "django-insecure-mm8cx0al6wo$$0hhv3&eevzsst9dbw&(5p$#9k(1rx%e@j+=$l",
)
```

**Best practice:** Never ship a fallback secret key, even one prefixed with
`"django-insecure-"`.  If the env var is absent, fail loudly in non-CI contexts.  For
automated test/CI environments, generate a random key on startup:

```python
from django.core.management.utils import get_random_secret_key
SECRET_KEY = os.environ.get("SECRET_KEY") or get_random_secret_key()
```

**Why it matters:** A committed fallback key can be accidentally used in production if
an env var is ever omitted from a deploy configuration, leading to a critical security
vulnerability (session forgery, cookie tampering, etc.).

## 3. Documentation Comment References Wrong Django Version

**Current state:**

```python
# Generated by 'django-admin startproject' using Django 3.2.
# For more information on this file, see
# https://docs.djangoproject.com/en/4.0/topics/settings/
```

The file was generated for Django 3.2 but links to the Django 4.0 docs.  The project
`Pipfile` pins `django = "==4.1.7"`.

**Best practice:** Update the header comment to accurately reflect the Django version
in use, and link to the appropriate version of the documentation.

**Why it matters:** Misleading version references cause confusion when developers look
up setting details in the linked documentation.

## 4. `ALLOWED_HOSTS` in Development Includes a Production Domain

**Current state:**

```python
ALLOWED_HOSTS = [
    "localhost",
    "127.0.0.1",
    "flynnt-knapp-8e0b83ab9b88.herokuapp.com",  # production domain in development config
]
```

**Best practice:** The development `ALLOWED_HOSTS` list should only contain local
addresses.  Production domains belong exclusively in the production config block.

**Why it matters:** Including a production domain in development `ALLOWED_HOSTS` could
enable request-forging exploits in local environments and confuses environment
boundaries.

---

## 5. `CELERY_ENABLE_UTC = False` Alongside `USE_TZ = True`

**Current state:**

```python
USE_TZ = True
CELERY_ENABLE_UTC = False
```

**Best practice:** When Django has `USE_TZ = True`, Celery should also use UTC
(`CELERY_ENABLE_UTC = True` or simply omit it, as `True` is the default in Celery 4+).
Mixing timezone-aware Django datetimes with Celery's UTC-disabled mode leads to subtle
time-comparison bugs, especially around scheduled tasks and `next_send` fields.

**Why it matters:** `CELERY_TIMEZONE = "America/New_York"` already localises display
times; enabling UTC in Celery for storage is not in conflict with that.

## 6. `DEFAULT_FILE_STORAGE` Uses the Deprecated Setting

**Current state:**

```python
DEFAULT_FILE_STORAGE = "storages.backends.s3boto3.S3Boto3Storage"
```

**Best practice (Django 4.2+):** Use the new `STORAGES` dictionary:

```python
STORAGES = {
    "default": {
        "BACKEND": "storages.backends.s3boto3.S3Boto3Storage",
    },
    "staticfiles": {
        "BACKEND": "whitenoise.storage.CompressedManifestStaticFilesStorage",
    },
}
```

**Why it matters:** `DEFAULT_FILE_STORAGE` was deprecated in Django 4.2 and will be
removed in a future version.  Migrating now avoids a breaking change during a future
upgrade.

## 7. WhiteNoise Middleware Position

**Current state:**

```python
if ENVIRONMENT == "production":
    MIDDLEWARE = MIDDLEWARE + ["whitenoise.middleware.WhiteNoiseMiddleware"]
```

WhiteNoise is appended to the **end** of the middleware list.

**Best practice:** WhiteNoise should be placed **immediately after**
`SecurityMiddleware` (second position) for it to serve static files efficiently and
before any other middleware that adds overhead:

```python
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "whitenoise.middleware.WhiteNoiseMiddleware",  # second position
    ...
]
```

**Why it matters:** Placing WhiteNoise at the end means every request passes through all
other middleware before WhiteNoise can short-circuit static file responses, reducing
performance for static asset requests.

---

## 8. Missing `STATIC_ROOT` / `STATICFILES_STORAGE` in Production for WhiteNoise

**Current state:** `STATIC_ROOT` is set only in production.  `STATICFILES_STORAGE` is
never set, so WhiteNoise's compressed/hashed storage backend is not used.

**Best practice:** In production, set:

```python
STATICFILES_STORAGE = "whitenoise.storage.CompressedManifestStaticFilesStorage"
```

(or the equivalent `STORAGES` key) to enable WhiteNoise's compressed + hashed file
serving and cache-busting.

**Why it matters:** Without the hashed storage backend, browsers may serve stale static
assets after a deploy.

## 9. AWS Credentials Always Loaded Regardless of Environment

**Current state:** AWS settings (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, etc.)
are always loaded from environment variables, even in development where S3 is not used.

**Best practice:** Guard AWS/S3 settings behind the production block:

```python
if ENVIRONMENT == "production":
    AWS_ACCESS_KEY_ID = os.getenv("AWS_ACCESS_KEY_ID")
    # ...
    DEFAULT_FILE_STORAGE = "storages.backends.s3boto3.S3Boto3Storage"
```

**Why it matters:** Loading AWS credentials in development when they are absent produces
confusing `None` values that can cause errors in library initialisation.  It also means
any accidental local file upload could target S3 if credentials are present in a
developer's shell.

## 10. `AWS_S3_OBJECT_PARAMETERS` Sets Public ACL

**Current state:**

```python
AWS_S3_OBJECT_PARAMETERS = {
    "ACL": "public-read",
    "CacheControl": "max-age=86400",
}
```

**Best practice:** AWS S3 now **blocks public ACLs by default** ("Block Public Access"
is enabled on new buckets).  Using `"ACL": "public-read"` will fail unless the bucket's
Block Public Access settings are explicitly disabled.  The modern approach for serving
public media files is to use a CloudFront distribution in front of a private S3 bucket
or to use pre-signed URLs.  If public access is genuinely required, it must be
explicitly justified and the bucket's Block Public Access must be configured carefully.

**Why it matters:** This is a potential deployment blocker and a security concern if the
bucket configuration is changed by AWS policy in the future.

## 11. `EMAIL_PORT` Is a String, Not an Integer

**Current state:**

```python
EMAIL_PORT = os.getenv("EMAIL_PORT")
```

`os.getenv()` always returns a string.  Django's `smtplib` integration expects
`EMAIL_PORT` to be an integer.

**Best practice:**

```python
EMAIL_PORT = int(os.getenv("EMAIL_PORT", "587"))
```

**Why it matters:** Passing a string for `EMAIL_PORT` will raise a `TypeError` the
first time Django tries to send an email in production.

## 12. No `CSRF_TRUSTED_ORIGINS` for Production

**Current state:** `CSRF_TRUSTED_ORIGINS` is not set.

**Best practice (required in Django 4.0+):** The full-domain CSRF check introduced in
Django 4.0 requires `CSRF_TRUSTED_ORIGINS` to be set for any production domain that
differs from the canonical `ALLOWED_HOSTS` entries (e.g. when behind a reverse proxy or
CDN):

```python
CSRF_TRUSTED_ORIGINS = [
    "https://flynnt-knapp-8e0b83ab9b88.herokuapp.com",
    "https://dev.quarterdeck.flynntknapp.com",
]
```

**Why it matters:** Without this, cross-origin POST requests (e.g. from a custom domain
alias) will fail with a CSRF 403 error.

## 13. `LOGGING` Config Only Covers `celery`

**Current state:** The `LOGGING` dictionary only defines a handler for the `celery`
logger.  Django's own request/security/database loggers are unconfigured.

**Best practice:** Add a `root` logger or a `django` logger entry so that application
errors, warnings, and security events are captured in production logs:

```python
"loggers": {
    "django": {
        "handlers": ["console"],
        "level": "WARNING",
    },
    "celery": {
        "handlers": ["console"],
        "level": "INFO",
        "propagate": True,
    },
},
```

**Why it matters:** Without this, Django's own error and security log messages
(including 500 errors in production) are silently dropped.

## 14. `REST_FRAMEWORK` Default Authentication Includes `BasicAuthentication`

**Current state:**

```python
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework.authentication.SessionAuthentication",
        "rest_framework.authentication.BasicAuthentication",
    ],
}
```

**Best practice:** `BasicAuthentication` transmits credentials (username + password) as
a Base64-encoded header on every request.  Although safe over HTTPS, it is generally
considered an anti-pattern for browser-facing APIs because credentials are not
automatically invalidated on logout.

**Recommendation:** Remove `BasicAuthentication` if it is not explicitly required.  If
API access is needed outside the browser session, prefer token-based auth
(`TokenAuthentication` from DRF or `SessionAuthentication` for same-origin SPA access).

---

## 15. `MAINTENANCE_MODE` Variable Not Exposed in Settings Docs / README

**Current state:** `MAINTENANCE_MODE` is implemented and wired to custom middleware
(`config.middleware.SuperuserMaintenanceMiddleware`) but is not documented.

**Best practice:** Document operational toggles like `MAINTENANCE_MODE` in the project
README or a runbook so that team members know how to activate/deactivate maintenance
mode in production.
